# BromeoRemote — Roadmap

## v1 — MVP (dit is wat er nu gebouwd is)

- [x] BromeoRemote-ID + sessiewachtwoord per apparaat
- [x] Signaling server (ID-koppeling, WebRTC-handshake brokeren)
- [x] Verbinden via ID + wachtwoord
- [x] Acceptatiedialoog bij inkomende verbinding (host moet expliciet toestaan)
- [x] Live schermdeling (WebRTC video)
- [x] Volledige besturing op afstand (muis + toetsenbord)
- [x] Bestandsoverdracht (dubbelzijdig, drag & drop)
- [x] Klembord-synchronisatie (tekst)
- [x] Permanente "je scherm wordt gedeeld"-statusbalk + paniekknop (sessie beëindigen + wachtwoord wijzigen)
- [x] Verbindingskwaliteit-indicator (fps/resolutie/latency zichtbaar)
- [x] Herbruikbare "onbeheerde toegang"-modus met vast wachtwoord
- [x] Branding met logo.png, licht/donker thema
- [x] Agent-notificatiebrug: lokale `/notify` + `/confirm` API zodat tools als Google Antigravity je overal kunnen bereiken zodra ze een bevestiging nodig hebben (zie `docs/ANTIGRAVITY.md`)
- [x] Opgeslagen/vertrouwde apparaten: versleuteld bewaard (Electron `safeStorage`/OS-keychain), één-tik verbinden, direct bruikbaar vanuit "Bekijk live" op een agent-melding
- [x] Rollen: "alleen bekijken" (geen muis-/toetsenbordbesturing) vs volledige controle, per verbinding instelbaar en per opgeslagen apparaat — door de **host** afgedwongen, niet enkel door de viewer-UI verborgen
- [x] Sessie-opname: lokaal WebM-bestand van wat je ziet tijdens de sessie (start/stop-knop, timer, opslaan via bestandsdialoog)
- [x] Sessie-samenvatting na afloop (duur, aantal overgezette bestanden) — verschijnt automatisch bij het beëindigen van een sessie

- [x] Chat-paneel tijdens sessie: eigen datachannel, beschikbaar voor zowel host (in de deel-balk) als viewer (in de sessiebalk)

- [x] Wake-on-LAN: MAC-adres opslaan bij een opgeslagen apparaat, magic packet versturen met één klik (werkt alleen binnen hetzelfde lokale netwerk als het slapende apparaat, of via een router die WoL-broadcasts doorstuurt)

- [x] Externe herstart + automatisch herverbinden: knop in de sessiebalk (verborgen bij "alleen-kijken", en door de host afgedwongen net als besturing), met bevestigingsdialoog en een automatische herverbindingspoging elke 15s (max. ~5 min) nadat de host offline gaat

- [x] Multi-monitor: host stuurt zijn schermenlijst zodra verbonden (bij 2+ schermen), viewer krijgt een dropdown om te wisselen — via `RTCRtpSender.replaceTrack`, dus zonder de verbinding opnieuw op te zetten. *Volledige pijplijn (enumeratie → wisselverzoek → replaceTrack) geverifieerd, maar het daadwerkelijke wisselen tussen twee fysiek verschillende beelden kon niet visueel getest worden — de ontwikkelmachine heeft maar één monitor.*

- [x] Privacyscherm (curtain mode, Windows): schakelt het fysieke beeldscherm van de host uit zodra een sessie start (optioneel, aan/uit-schakelaar), plus een handmatige aan/uit-knop tijdens de sessie zelf. Schermdeling blijft gewoon doorlopen — dit is een privacyscherm tegen meekijkende omstanders, geen invoerblokkade (lokale muis/toetsenbord wekken het scherm gewoon weer). Bijvangst: een `bye`-signaal wordt nu bij elke bewuste sessie-beëindiging verstuurd, zodat de andere kant direct opruimt in plaats van op een WebRTC-timeout te wachten.

- [x] Adresboek: groepen (vrije tekst, alfabetisch gesorteerd) en favorieten (⭐, altijd bovenaan) bovenop de bestaande opgeslagen apparaten — versleuteld opgeslagen zoals de rest van het adresboek, getest inclusief herstart-persistentie

- [x] Two-factor authenticatie (TOTP, RFC 6238) voor onbeheerde toegang: eigen implementatie op Node's `crypto` (geen externe library), geverifieerd tegen de officiële RFC 6238-testvectoren en end-to-end getest (geen code → foute code → juiste code). Secret staat versleuteld opgeslagen (`safeStorage`); handmatige sleutel-invoer in de authenticator-app (geen QR-code in v1).

## v2 — Uitbreiding

- [x] Automatische updates van de client: `electron-updater` + NSIS-installer (naast de bestaande portable exe). Controleert bij opstarten en via een knop onderaan het venster; downloadt en installeert bij herstart. Zelf gehost (generic provider) op je eigen VPS, geen GitHub-account nodig — zie `docs/DEPLOY.md` §5. De portable exe slaat auto-update bewust over (geen vaste installatielocatie om zichzelf te vervangen) en meldt dat ook duidelijk. Getest: dev-modus (nette foutmelding, geen crash), geïnstalleerde build tegen een niet-bestaande updateserver (nette netwerkfout, geen crash), en de portable build (toont expliciet dat auto-update niet geldt). Onderweg een race conditie gevonden en gefixt: de eerste check gebeurde te vroeg, vóórdat de renderer zijn listener had geregistreerd — nu start de renderer zelf de eerste check, pas na registratie.

## v3 — Verder uitbouwen

- [x] Mobiele viewer-app (Android): React Native-app (`mobile/`) om vanaf je telefoon een andere pc te bekijken/besturen — verbinden via ID + wachtwoord, live video mét systeemgeluid, touch-naar-muis-vertaling (tik = klik, sleep = muisbeweging, lang indrukken = rechtsklik, twee vingers = scrollen, knijpen/dubbeltik = in-/uitzoomen met behoud van klik-nauwkeurigheid), horizontale weergave, on-screen toetsenbord-brug, en agent-bevestigingen (zie hieronder) die ook mid-sessie bereikbaar blijven. Zie `docs/MOBILE.md`. *iOS niet gebouwd — vereist Xcode/macOS, niet beschikbaar op de ontwikkelmachine (Windows).*
- [x] Muis-modus (trackpad-stijl) in de mobiele viewer: een 👆/🖱️-schakelaar in de sessiebalk naast de bestaande tik-modus — een zichtbare cursor-stip die je relatief verplaatst door te slepen (zoals een laptop-trackpad, in plaats van absoluut tikken-op-een-plek), met tik = klik, lang indrukken = rechtsklik, lang indrukken + slepen = klikken-en-slepen. Rechtstreeks geïnspireerd op TeamViewer's "Interactiemethode"-instelling. Getest tegen een echte desktop-sessie: cursor volgt de sleepbeweging met de juiste richting/gevoeligheid, klikken en rechtsklikken komen daadwerkelijk aan op de host.
  **Later 1-op-1 gelijkgetrokken met TeamViewer's eigen "Interactiemethode"-schermen** (na het opnieuw bekijken van die exacte referentieschermen): (1) muis-modus' klik-en-sleep activeert nu op de **tweede tik van een dubbeltik** die meteen doorslepen wordt, in plaats van op "lang stilhouden" — een gewone trage sleepbeweging kan het dus nooit meer per ongeluk activeren, hoe lang hij ook duurt. (2) Tik-modus kreeg dezelfde drie-weg-herkenning als TeamViewer's touch-modus: één vinger meteen slepen = scrollen (stuurt scroll-wheel naar de host, geen cursorbeweging), lang indrukken en dán pas slepen = klikken-en-slepen, tik = klik — voorheen was élke sleepbeweging in tik-modus gewoon absolute muisbeweging, wat nu alleen nog via muis-modus kan. (3) Twee vingers slepen is in beide modi nu "schuiven" (pant het lokaal ingezoomde beeld, raakt de sessie niet aan) in plaats van scrollen — heeft vanzelf geen effect zolang je niet ingezoomd bent. (4) Host's video-encoder staat nu op `degradationPreference: "maintain-resolution"` (client én mobiel-als-host) zodat bij weinig bandbreedte de framerate zakt in plaats van de resolutie — leesbaarheid van tekst weegt zwaarder dan vloeiendheid.
  **Videokwaliteit vastgepind op ~300kbps, echte oorzaak gevonden**: PC-naar-PC op dezelfde machine (0ms RTT, dus geen netwerkbeperking mogelijk) toonde nog steeds precies 300kbps — dat sluit een netwerkprobleem uit en wijst op de encoder zelf. `MediaStreamTrack.contentHint` stond nergens ingesteld: zonder die hint neemt Chromium's encoder aan dat het gewone bewegende video is (webcam-stijl) en mikt hij bewust op een bescheiden bitrate, in plaats van te herkennen dat het een statisch, tekstrijk beeldscherm is dat juist scherpte nodig heeft. Nu overal op `"detail"` gezet zodra de capture-stream binnenkomt (client's `acceptAsHost` én `replaceVideoTrack` bij schermwisselen, mobiel-als-host's `acceptAsHost`) — dit is een bekende, gedocumenteerde WebRTC-praktijk specifiek voor schermdelen, los van de eerdere `degradationPreference`-fix (die gaat over wat er *bij bandbreedtedruk* wordt opgeofferd, dit gaat over het encoder-gedrag vanaf het begin). *Nog te bevestigen of dit de bitrate daadwerkelijk omhoog krijgt op echte apparaten — kon niet zelf live getest worden.*
  **Vier bugs gemeld en gefixt na echt gebruik op een fysiek toestel** (geen van de vier kwam naar boven op de emulator, die geen multitouch simuleert): (1) "lang indrukken + slepen = selecteren" activeerde per ongeluk ook bij een gewone, langzame cursor-verplaatsing — de check keek alleen naar *verstreken tijd* sinds het neerzetten van de vinger, niet of de vinger stil had gestaan; nu vereist het écht stilhouden (< 12px afwijking) gedurende de 500ms-drempel voordat het als klik-en-sleep telt. (2) Knijpen om te zoomen werkte vrijwel nooit, omdat de twee vingers zelden exact in hetzelfde frame neerkomen — de pinch-tracking werd alleen gestart in `onPanResponderGrant`, dus als de tweede vinger iets later volgde (de normale situatie) deed de move-handler stilzwijgend niets. Nu initialiseert de pinch-tracking ook lazy zodra een tweede vinger tijdens een lopende gesture verschijnt. (3) De "werkbalk uitklappen"-knop (na inklappen) reageerde niet op tikken: die knop zat als kind ín de View met de `PanResponder`, die alle aanrakingen in dat gebied opeist vóórdat de knop zijn eigen `onPress` kan afvuren — nu heeft alleen een binnenste laag (rond de video) de pan-handlers, en zit de uitklap-knop daarbuiten als sibling (maar nog wel binnen dezelfde ouder, voor de SurfaceView-stapelvolgorde-truc). (4) Tijdens het inzoomen leek het beeld heen en weer te "schuiven" — de knijpen-vs-scrollen-herkenning stuurde standaard scroll-wheel-invoer naar de host zodra twee vingers bewogen, tót de vingerafstand meer dan 12% was veranderd; omdat een echte knijpbeweging zelden vanaf frame 1 perfect symmetrisch is, werd de eerste fase van bijna elke pinch als scrollen naar de host gestuurd (het externe scherm scrolde dus echt). Nu wacht de herkenning op een duidelijk signaal (afstandsverandering ≥6% of vingermiddelpunt-verschuiving ≥14px) voordat er iets gebeurt, in plaats van standaard "scrollen" te versturen tijdens die onduidelijke eerste fase.
- [x] Eigen app-branding (mobiel): het echte BromeoRemote-icoon (`icon.png`) vervangt het standaard React Native-icoon op alle schermdichtheden (`ic_launcher`/`ic_launcher_round`), plus een donker native opstartscherm met logo (`LaunchTheme`/`launch_screen.xml`, zichtbaar direct bij het opstarten, vóór de JS-bundel laadt) dat overloopt in een bijpassend "Verbinden…"-laadscherm in de app zelf.
- [ ] Mobiele viewer-app (iOS) — zelfde app, wacht op een macOS-ontwikkelomgeving
- [x] Mobiel apparaat als host (telefoon van jezelf op afstand bekijken/bedienen): rotatiewachtwoord + toestemmingsdialoog (zelfde patroon als desktop), schermdelen via `react-native-webrtc`'s ingebouwde MediaProjection-support, en echte tik-/veegbediening vanaf de pc via een eigen `RemoteControlAccessibilityService` (native Kotlin — Android staat gewone apps sowieso niet toe om aanraking in andere apps te injecteren, dit is hetzelfde mechanisme als TeamViewer QuickSupport/AirDroid). Handmatig in te schakelen via Instellingen → Toegankelijkheid, met statusweergave + directe link in de app. Geen toetsenbordondersteuning in v1 (ander mechanisme dan gebaren-dispatch). Zie `docs/MOBILE.md` §4. *Pijplijn end-to-end geverifieerd tot en met een actieve WebRTC-verbinding met correct geconfigureerde encoder; de daadwerkelijke videoframes zelf nog niet bevestigd — de ontwikkel-emulator produceert structureel 0 encoded frames (ook na volledige herstart), een bekende categorie MediaProjection/emulatorbeperkingen. Nog te bevestigen op een echt toestel.*
- [x] Echte mobiele push-notificaties (FCM) voor de agent-notificatiebrug, zodat meldingen ook aankomen als de telefoon-app dicht/achtergrond staat — server stuurt bij elke melding zowel de bestaande WebSocket-melding als een FCM-push (met dedupe op notificatie-id aan de mobiele kant). Vereist een eigen Firebase-project (niet iets dat namens jou aangemaakt kan worden) — zie `docs/MOBILE.md` §5 voor de setup; zonder dat blijft alleen de WebSocket-melding werken. APNs (iOS) nog niet van toepassing zolang er geen iOS-build is.
- [x] Sessiebalk-herontwerp (mobiel), TeamViewer-stijl: icoon-knoppen in plaats van tekst/emoji-mix, inklapbaar tot een klein "︿"-bolletje dat weer terug uitklapt (meer beeldruimte tijdens de sessie), een apart **Snelle acties**-paneel (⚡, los van de bestaande **Snelkoppelingen**-balk onder ⌥) met **Vergrendelen** en **Herstarten op afstand**, en een instellingenscherm (⚙️) met "Externe cursor tonen" (aan/uit voor de muis-modus-cursorstip). Vergrendelen/herstarten zijn nieuwe `SystemCommand`-berichten (`lock-request` naast het bestaande `restart-request`) die de **host** net zo afdwingt als de rest (genegeerd bij een alleen-kijken-sessie); op Windows via `rundll32 user32.dll,LockWorkStation`. Ook toegevoegd aan de desktop-viewer zelf (naast de bestaande herstart-knop), niet enkel de mobiele app.
- [ ] Ctrl+Alt+Del op afstand versturen (**experimenteel, niet werkend bevestigd**): geen klassieke Windows-service of kernel-driver (zoals TeamViewer/RustDesk dat oplossen) — in plaats daarvan een SYSTEM-geprivilegieerde Taakplanner-taak **zonder trigger** (draait nooit vanzelf, alleen op aanvraag via `schtasks /run`), die `sas.dll!SendSAS(false)` aanroept via `koffi`. Vereist eenmalig de `SoftwareSASGeneration`-registrysleutel + taakregistratie via een UAC-bevestiging, expliciet getriggerd via een kaart "Ctrl+Alt+Del op afstand ontvangen (experimenteel)" op het beginscherm — nooit stilzwijgend door de app zelf. Nieuwe `ctrl-alt-del-request`/`ctrl-alt-del-status`-systeemberichten (zelfde patroon als `block-input`/`block-input-status`); genegeerd bij een alleen-kijken-sessie.
  **Live getest op een echte Windows 11-machine (build 10.0.26200), twee bugs gevonden en gefixt onderweg:** `Register-ScheduledTask` met een SYSTEM+Highest-principal geeft standaard alleen Administrators query/run-rechten — zowel het statuscheck (`isSasInstalled`) als het versturen zelf (`sendCtrlAltDel`) faalden daardoor met "Toegang geweigerd" voor een gewone gebruiker, ook al was alles correct geregistreerd. Opgelost door na registratie expliciet een ACL te zetten (`SetSecurityDescriptor` via de Task Scheduler COM-API) die Authenticated Users lees-/uitvoerrecht geeft — na die fix werken installeren, statuscheck, versturen én uitschakelen allemaal end-to-end correct (herbevestigd via de echte gecompileerde code, niet enkel losse testscripts).
  **Wat nog steeds niet werkt:** de taak draait succesvol als SYSTEM (exit code 0, geen fouten), maar `SendSAS` zelf heeft geen zichtbaar effect — het Ctrl+Alt+Del-beveiligingsscherm verschijnt niet. Oorzaak onbevestigd: mogelijk werkt deze API niet meer (of is ingeperkt) op recente Windows-versies, of vereist de interne check specifiek een via SCM geregistreerde Windows-service in plaats van een Taakplanner-taak met een SYSTEM-principal — die twee zien er voor de meeste doeleinden identiek uit (allebei draaien als SYSTEM) maar zijn architectonisch verschillende Windows-subsystemen. Verder onderzoek nodig (of overstappen op een echte service/driver) voordat dit als werkend kan gelden. Zie code-commentaar in `client/src/main/sasControl.ts`/`sasHelper.ts` voor het volledige verhaal.
- [x] Externe gebruikersinvoer blokkeren tijdens een sessie (host's eigen muis/toetsenbord uitschakelen): nieuw `block-input`-systeembericht, host-side afgehandeld via de Win32 `BlockInput`-API — via `koffi` (FFI zonder eigen native addon/node-gyp-compilatiestap) in plaats van een los hulpprogramma. Genegeerd bij een alleen-kijken-sessie, net als vergrendelen/herstarten. **Twee onafhankelijke veiligheidsnetten** zorgen dat de host nooit blijvend op slot komt te staan: (1) `endSession()` (bij elke sessie-einde, ongeacht de oorzaak — bewuste ophang, netwerkstoring, ICE-fout) roept expliciet `blockInput(false)` aan, en (2) Windows zelf heft de blokkade automatisch op zodra het aanroepende proces stopt (`app.on("before-quit")` roept het ook expliciet aan, als extra insurance). Knop in zowel de desktop-viewer (sessiebalk, wisselt van stijl als hij actief is) als de mobiele **Snelle acties**.
- [x] Kwaliteit-instelling vanuit de viewer (Automatisch/Hoog/Laag): nieuw `quality-request`-systeembericht dat de host's uitgaande videobitrate begrenst via `RTCRtpSender.setParameters` (`encodings[0].maxBitrate`) — "Automatisch" laat WebRTC's eigen congestion control ongelimiteerd, "Hoog"/"Laag" zetten een harde bitrate-cap (8/0,8 Mbps) voor respectievelijk scherpte of een trage verbinding. Beschikbaar in zowel de desktop-viewer (dropdown naast de schermkeuze) als de mobiele viewer (Sessie-instellingen). *Resolutie zelf (daadwerkelijk lagere capture-resolutie) blijft nog open — dat vereist opnieuw `getDisplayMedia` aanroepen met constraints, ingrijpender dan een bitrate-cap.*
- [ ] Resolutie-instelling vanuit de viewer (daadwerkelijk lagere capture-resolutie, niet enkel bitrate): vereist opnieuw capturen via `getDisplayMedia` met resolutie-constraints op de host, met de bijbehorende korte onderbreking van de videotrack (zelfde patroon als schermwisselen).
- [x] Adresboek (mobiel): "Dit apparaat onthouden" bij het verbinden slaat `{id, label, passwordHash}` lokaal op (`AsyncStorage`, niet versleuteld zoals de desktop's `safeStorage`/OS-keychain — bewuste kleinere-scope-keuze, zie hieronder), met favorieten (⭐, altijd bovenaan, verder alfabetisch) en één-tik verbinden zonder het wachtwoord opnieuw in te typen. Werkt zonder ooit het plaintext-wachtwoord op te slaan of opnieuw te versturen — de opgeslagen `passwordHash` is letterlijk hetzelfde veld dat het `connect-request`-bericht al over de lijn stuurt, dus één-tik verbinden hergebruikt 'm direct. Geen groepen (desktop heeft die wel) en geen Wake-on-LAN vanuit mobiel in deze versie.
  *Bekende beperking t.o.v. desktop: platte `AsyncStorage` in plaats van OS-keychain-versleuteling. Voor een gehashte sessiewachtwoord (niet het wachtwoord zelf) een redelijke afweging voor v1 — `react-native-keychain` zou dit gelijktrekken met desktop als dat later gewenst is.*
- [x] Professionaliseringsronde (mobiel), geen nieuwe functies maar bestaande dingen afwerken:
  - **Ingestelde kwaliteit/cursor-voorkeur blijft bewaard** tussen app-starts (`AsyncStorage`, zelfde patroon als desktop's `localStorage`) en wordt automatisch opnieuw toegepast zodra een nieuwe sessie start. Onderweg een echte bug gevonden en gefixt: `MobileSession.sendSystemCommand()` liet berichten die vóór het openen van het datakanaal werden verstuurd stilzwijgend vallen (geen wachtrij, in tegenstelling tot de desktop-`PeerSession` die dat al wel had) — nu met dezelfde "wachten tot open, dan alsnog versturen"-wachtrij als desktop.
  - **Niet-blokkerende toast-meldingen** (bv. "Vergrendelen aangevraagd.", "Ctrl+Alt+Del verzonden.", "Apparaat opgeslagen.") voor acties die voorheen helemaal geen feedback gaven — `Alert.alert` (modaal, moet weggeklikt worden) blijft gereserveerd voor mislukte pogingen die echt aandacht nodig hebben.
  - **`accessibilityLabel`/`accessibilityRole`** op alle icoon-only sessiebalk-knoppen (muis-/tikmodus, snelle acties, snelkoppelingen, toetsenbord, instellingen, verbreken, in-/uitklappen) — voorheen had geen enkele knop dit.
  - *Nog open (bekeken maar bewust niet meegenomen in deze ronde):* echte iconen in plaats van emoji (vereist een nieuwe native afhankelijkheid zoals `react-native-vector-icons`, een grotere beslissing).
- [x] Chat op mobiel (💬 in de sessiebalk, rode stip bij ongelezen berichten): puur een ontbrekende UI, geen nieuw protocolwerk — `MobileSession` had `sendChat`/`onChatMessage` en het datakanaal al liggen (client en server ondersteunden chat al), `App.tsx` bouwde er alleen nog geen scherm omheen. Alleen de viewer-rol in deze versie; chat tijdens een sessie waarin de telefoon zelf host is nog niet gebouwd.
- [x] Bestandsoverdracht op mobiel (📁 in de sessiebalk): het gedeelde `FileMessage`-protocol werkte al voor desktop, mobiel miste alleen de datakanaal-wiring en UI. Twee nieuwe native afhankelijkheden bewust gekozen op basis van onderhoudsstatus (de oudere `react-native-document-picker`/`react-native-fs` zijn al ruim een jaar niet bijgewerkt) in plaats van stilzwijgend toegevoegd: `@react-native-documents/picker` (bestand kiezen om te versturen) en `react-native-blob-util` (ontvangen bestanden wegschrijven naar de Downloads-map, incl. media-scan). Zelfde chunking (48KB, back-pressure op `bufferedAmount`) en "geen per-bestand accepteren/weigeren, de sessie zelf is de toestemmingsgrens"-gedrag als de desktop-app. **Geverifieerd met een echte Gradle-build** (`assembleDebug`, `BUILD SUCCESSFUL`, beide nieuwe native modules correct ge-autolinked) — niet enkel `tsc`. Alleen de viewer-rol in deze versie.
- [x] Vier kleinere desktop-pariteitspunten op mobiel, alle zonder nieuwe afhankelijkheid:
  - **Multi-monitor wisselen**: `monitor-list`/`switch-monitor`-berichten bestonden al in het protocol maar mobiel deed er niets mee — nu een schermkiezer in Sessie-instellingen zodra de host er 2+ meldt.
  - **Automatisch opnieuw verbinden na herstart**: exact dezelfde `scheduleAutoReconnect`-logica overgenomen van de desktop-viewer (15s interval, ~20 pogingen/5 min, stopt zodra er weer een sessie is).
  - **TOTP-invoer bij 2FA-hosts**: vult een echte functionele leemte in — mobiel kon voorheen helemaal niet verbinden met een host die 2FA vereist (de server/host sturen `totp-required`/`bad-totp` als weigerreden, maar mobiel had geen scherm om de code in te vullen en opnieuw te proberen). Nu een eigen invoerscherm, zelfde retry-patroon als desktop.
  - **Sessie-samenvatting**: toast bij het einde van een sessie met duur + aantal overgezette bestanden, zelfde tekst als desktop's `showSessionSummary()` — zonder desktop's opgeslagen sessiegeschiedenis/notities-functie, die is niet meegenomen.
- [ ] Teams/organisaties: gedeeld apparatenbeheer, audit log, admin-rollen
- [ ] VPN/netwerkbrug tussen twee sites

## Bewust buiten scope (voor nu)

- Eigen TURN-protocol bouwen — we hergebruiken coturn (industriestandaard, zie `ARCHITECTURE.md`).
- App store-distributie — v1 draait als lokaal geïnstalleerde/portable Electron-app.
- Remote print (TeamViewer-stijl): vereist een eigen virtuele printerdriver op de host die printopdrachten omleidt naar een printer bij de viewer. Dat is driverontwikkeling/-ondertekening, een wezenlijk ander soort werk dan de rest van deze Electron-app. Gebruik in de tussentijd de bestaande bestandsoverdracht: stuur het document en print het lokaal op je eigen printer.
